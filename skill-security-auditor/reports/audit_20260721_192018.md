## ⚠️ Headline Finding: Scanner Self-Exemption Bypass (unauthenticated)

This cycle's scan reports `skill-security-auditor` as **0.0/LOW ("Exempt")**. That is
**not because risk decreased** — it is because `risk_scorer.py` v0.2.3 added a
`_check_self_exempt()` function (see `references/risk_scorer.py:166-186`) that:

1. Reads the first 2000 characters of any `SKILL.md`.
2. If it finds a comment matching `<!-- audit:self-exempt reason: ... -->`, **skips
   scanning entirely** and force-returns `final_score=0.0`, `risk_level=LOW`.
3. This check has **no authentication, scope limit, or human sign-off** — any skill
   author (including a malicious one) can paste this exact comment into their own
   `SKILL.md` and make the scanner report a clean bill of health regardless of actual
   content.

`skill-security-auditor/SKILL.md` line 1 now contains exactly this comment:

```
<!-- audit:self-exempt reason: risk_scorer.py contains intentional static analysis
code (subprocess/eval patterns used for detection, not execution). Score 96.8 is
correct scanner behavior on its own .py files. -->
```

To verify, the scanner was re-run on a copy of `skill-security-auditor/` with that one
comment line stripped and nothing else changed:

| Run | Score | Level |
|-----|-------|-------|
| As-is (with self-exempt comment) | 0.0 | LOW ("Exempt") |
| Comment removed, same code | **100.0** | **BLOCKED** |

Two things stand out:

- The exemption's own stated justification cites a score of "96.8" — which does not
  match the actual unexempted score (100.0) produced by the current scanner version.
  The exemption text appears to have been carried over from the 2026-04-08 report
  without re-verification against the current code.
- Even granting that most of these hits are self-referential false positives (the
  scanner's own file contains the literal regex strings — e.g. `subprocess\.`,
  `eval\s*\(`, `~/\.ssh` — as *pattern definitions*, not executed code), the fix
  implemented is a **blanket, unauthenticated bypass** rather than a scoped
  suppression of the specific false-positive lines. As written, this mechanism is a
  known technique any future skill could use to defeat this very auditor.

**This finding is treated as informational/critical for this report — no code has
been changed.** Per the auditor's own constraints, edits to `risk_scorer.py` require
explicit user confirmation (see Improvement Options, below).

## Improvement Options

The following improvement was identified from this cycle's self_notes and from direct
inspection of the scanner. **No changes have been made to `risk_scorer.py`.**

### 1. Unauthenticated self-exempt bypass (self-note from: `skill-security-auditor`)

**Skill that triggered it:** `skill-security-auditor` (the auditor auditing itself)

**Exact note text:**
> "EXEMPT: risk_scorer.py contains intentional static analysis code (subprocess/eval patterns used for detection, not execution). Score 96.8 is correct scanner behavior on its own .py files."

**Root cause:** `_check_self_exempt()` in `references/risk_scorer.py:166-186`, wired
into `score_skill()` at `references/risk_scorer.py:311-330`, honors any
`<!-- audit:self-exempt reason: ... -->` comment found in the first 2000 characters
of a target's `SKILL.md`, unconditionally zeroing the score and skipping all scanning.
There is no check on who added the comment, no scoping to specific dimensions/lines,
and no cross-reference against the actual computed score (the cited "96.8" doesn't
even match the current unexempted result of 100.0).

**Specific change recommended in `risk_scorer.py`:**
- **File:** `skill-security-auditor/references/risk_scorer.py`
- **Location:** `_check_self_exempt()` (lines 166–186) and its call site in
  `score_skill()` (lines 311–330)
- **Current pattern:**
  ```python
  def _check_self_exempt(skill_path: Path) -> tuple[bool, str]:
      ...
      m = re.search(
          r"<!--\s*audit:self-exempt(?:\s+reason:\s*([^-].*?))?\s*-->",
          head, re.IGNORECASE | re.DOTALL
      )
      if m:
          reason = (m.group(1) or "").strip() or "no reason given"
          return True, reason
      return False, ""
  ```
  and in `score_skill()`:
  ```python
  exempt, exempt_reason = _check_self_exempt(skill_path)
  if exempt:
      zero_dims = [...]
      return SkillRiskReport(..., final_score=0.0, risk_level="LOW", ...)
  ```
- **Proposed fix:**
  1. Remove the ability for an in-repo comment to zero out a score unilaterally.
     Replace with an external, auditor-maintained allowlist file (e.g.
     `skill-security-auditor/known_fp_exemptions.json`, keyed by skill name +
     a hash of the skill's content at exemption time) that only *this tool's
     maintainer* can edit — not the skill author.
  2. Scope exemptions per-dimension/per-line rather than whole-report: an entry
     should suppress specific matched signals (e.g. "D2 credential-keyword hits
     inside the `SIGNALS` dict literal are pattern definitions, not secrets") rather
     than zeroing every dimension.
  3. Never silently drop from BLOCKED to LOW — cap the exemption discount (e.g. floor
     at "reviewed, no action" but keep the level visible as `EXEMPT-BLOCKED` in
     reporting) so a human always sees the true unmitigated score alongside the
     exemption rationale.
  4. If a self-declared comment mechanism is kept at all for convenience, require the
     reason text to include a content hash or version pin so stale exemptions (like
     the "96.8" mismatch found this cycle) are automatically invalidated when the
     underlying file changes.
