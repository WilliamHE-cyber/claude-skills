## 0. CRITICAL FINDING — Self-exempt mechanism is an unscoped scanner bypass

`risk_scorer.py`'s `_check_self_exempt()` (added in v0.2.3, `references/risk_scorer.py:166-186`) searches the first 2000 characters of **any** `SKILL.md` for the literal marker `<!-- audit:self-exempt reason: ... -->`. If found, `score_skill()` (`references/risk_scorer.py:311-330`) skips scanning entirely and hard-codes `final_score=0.0`, `risk_level="LOW"`, all seven dimensions zeroed, regardless of what the skill actually contains.

`skill-security-auditor/SKILL.md` line 1 carries exactly this marker, with a reason claiming: *"Score 96.8 is correct scanner behavior on its own .py files."* This is why this run reported the auditor itself as `0.0 / LOW / No action required`.

I re-ran the scanner against this skill with the self-exempt check disabled to get the ground-truth score. Result: **100.0 / BLOCKED** (all 7 dimensions capped at 10/10 — up slightly from 96.8 in the 2026-04-08 report because D6 also saturated this time). The prior report (`audit_20260408_202825.md`) had already scored and logged this honestly as BLOCKED with a note that the score was a self-referential false positive from the tool documenting its own regex signals — a reasonable read of *that* score. The problem is the fix that shipped afterward doesn't correct the false positive; it just hides the number.

Why this matters beyond "the report shows a nicer number":

- **The check is not actually "self"-scoped.** Nothing ties the exemption to `skill-security-auditor` specifically — `_check_self_exempt()` runs the same regex against every skill's `SKILL.md`. Any skill, benign or malicious, can paste `<!-- audit:self-exempt reason: ... -->` into its own frontmatter and unconditionally zero its score. There is no signature, allowlist, path restriction, or reviewer sign-off gating it — the skill grants itself the exemption.
- **It exempts everything, not just the false-positive dimensions.** Even taking the "documentation false positive" justification at face value, D6 (dependencies) has real hits in the un-exempted run (`--extra-index-url`, unpinned version specs in the changelog prose) that were never confirmed as FPs. The blanket exemption suppresses those along with the legitimate D1–D5/D7 documentation-pattern noise.
- **Downstream consumers can't tell the difference.** The JSON output for an exempted skill looks identical in shape to a genuinely clean scan (`final_score: 0.0`, empty `hits` arrays) — a pipeline that greps for `risk_level == "BLOCKED"` (like a naive version of this very audit) will silently pass a self-exempted skill through.
- **The tool's own self_notes text is written to read as reassurance** ("Score 96.8 is correct scanner behavior... EXEMPT") rather than as a flag for review — despite the SKILL.md's own three-layer protocol saying pre-check should "flag unexpected tool use" and treat exemptions with scrutiny.

**Recommendation:** Do not let a skill exempt itself via content inside its own directory. If self-referential documentation false-positives need suppression, scope the exemption to (a) a specific dimension, (b) an explicit line-range or file, and (c) an external allowlist maintained outside the audited skill's own tree (e.g. a file under `skill-security-auditor/` that names other skills, never itself) — mirroring the *per-dimension* `<!-- audit:exempt D1 reason: ... -->` pattern the report template already describes in Section 5, rather than the blanket `audit:self-exempt` that zeroes the whole report.

This is flagged here as a finding, not applied — per the audit protocol, `risk_scorer.py` was not modified.

## Improvement Options

The one non-empty `self_notes` entry this cycle, and the deeper issue it surfaces, are laid out here for explicit sign-off before any code changes are made.

**1. Skill:** `skill-security-auditor`
**Self-note text:** `EXEMPT: risk_scorer.py contains intentional static analysis code (subprocess/eval patterns used for detection, not execution). Score 96.8 is correct scanner behavior on its own .py files.`

**Recommended change to `skill-security-auditor/references/risk_scorer.py`:**

- **File location:** `_check_self_exempt()`, lines 166–186, and its call site in `score_skill()`, lines 311–330.
- **Current pattern:** Any `SKILL.md` containing `<!-- audit:self-exempt reason: ... --><br>` anywhere in its first 2000 characters causes `score_skill()` to return a hard-coded `final_score=0.0`, `risk_level="LOW"`, with every dimension zeroed and no hits recorded — for the entire skill, regardless of which dimensions actually had false positives.
- **Proposed fix:**
  - Remove the blanket `audit:self-exempt` path entirely, or restrict it so it can only ever suppress the specific dimensions named in the annotation (mirroring the already-documented per-dimension syntax in the report template: `<!-- audit:exempt D1 reason: ... -->`), never the whole report.
  - Move the authority to grant an exemption out of the audited skill's own directory. E.g., maintain `skill-security-auditor/exemptions.json` (or similar) listing `{skill_name, dimension, reason, approved_by, date}` — a file the target skill cannot edit about itself — and have `_check_self_exempt` (or its replacement) consult that instead of trusting a comment embedded in the thing being audited.
  - Keep the true per-dimension scores in the JSON/report output even when an exemption is applied (e.g. `dimensions: [...], exempted_dimensions: ["D1","D2",...], final_score_if_unexempted: 100.0`), so downstream consumers and future audits can still see what's being suppressed instead of a report that is indistinguishable from a clean scan.
  - Have `--all` summary output surface an explicit "N skill(s) running under active exemption" line so exemptions can't silently zero out a BLOCKED result in batch runs.
